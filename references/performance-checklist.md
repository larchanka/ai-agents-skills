# Чеклист производительности (Performance Checklist)

## Целевые показатели Core Web Vitals

| Метрика | Хорошо | Требует улучшения | Плохо |
|---------|--------|-------------------|-------|
| LCP (Largest Contentful Paint) | ≤ 2.5с | ≤ 4.0с | > 4.0с |
| INP (Interaction to Next Paint) | ≤ 200мс | ≤ 500мс | > 500мс |
| CLS (Cumulative Layout Shift) | ≤ 0.1 | ≤ 0.25 | > 0.25 |

## Диагностика TTFB

Когда TTFB (время до получения первого байта) слишком велико (> 800мс), проверь каждый компонент на вкладке Network в DevTools:

- [ ] **Разрешение DNS (DNS resolution)** медленное → добавь `<link rel="dns-prefetch">` или `<link rel="preconnect">` для известных источников.
- [ ] **Рукопожатие TCP/TLS (TCP/TLS handshake)** медленное → включи HTTP/2, рассмотри развертывание на границе (edge deployment), проверь заголовок keep-alive.
- [ ] **Обработка на сервере (Server processing)** медленная → профилируй бэкенд, проверь медленные запросы, добавь кэширование.

## Чеклист для фронтенда

### Изображения
- [ ] Изображения используют современные форматы (WebP, AVIF).
- [ ] Размеры изображений адаптивны (`srcset` и `sizes`).
- [ ] Изображения и элементы `<source>` имеют явно указанные `width` и `height` (предотвращает CLS при изменении макета).
- [ ] Изображения ниже первого экрана (below-the-fold) используют `loading="lazy"` и `decoding="async"`.
- [ ] Главные изображения (Hero/LCP) используют `fetchpriority="high"` и не загружаются лениво.

### JavaScript
- [ ] Размер бандла при начальной загрузке составляет менее 200 КБ (в сжатом gzip виде).
- [ ] Настроено разделение кода (code splitting) с динамическим `import()` для маршрутов и «тяжелых» фич.
- [ ] Включен Tree shaking (убедись, что зависимость поставляется в формате ESM и помечена как `sideEffects: false`).
- [ ] Нет блокирующего JavaScript в `<head>` (используй `defer` или `async`).
- [ ] Тяжелые вычисления вынесены в Web Workers (если применимо).
- [ ] Используется `React.memo()` на ресурсоемких компонентах, которые часто перерендериваются с теми же пропсами.
- [ ] Используются `useMemo()` / `useCallback()` только там, где профилирование показывает реальную пользу.
- [ ] Длинные задачи (> 50мс) разбиваются на части, чтобы держать главный поток свободным — это главный рычаг для улучшения INP.
- [ ] Паттерн `yieldToMain` используется внутри долгих циклов, чтобы события ввода могли выполняться между итерациями.
- [ ] Используются современные API планирования, где они доступны: `scheduler.yield()` (предпочтительно), `scheduler.postTask()` с приоритетами, `isInputPending()` для передачи управления только при наличии ввода.
- [ ] Используется `requestIdleCallback` для некритичной работы, которую можно отложить (отправка аналитики, предзагрузка, прогрев кэша).
- [ ] Выполнение некритичных задач вынесено за пределы обработчиков событий (например, отправка аналитики, логирование), чтобы не задерживать ответ на взаимодействие пользователя с интерфейсом.
- [ ] Сторонние скрипты загружаются с атрибутами `async` / `defer`, проверены на размер и скрыты за фасадом, если они слишком тяжелые (виджеты чатов, эмбеды).

### CSS
- [ ] Критический CSS встроен в код (inlined) или предзагружен.
- [ ] Нет блокирующего рендеринг CSS для некритичных стилей.
- [ ] Отсутствуют накладные расходы CSS-in-JS в продакшне (используй экстракцию в статические CSS-файлы).

### Шрифты
- [ ] Использование ограничено 2–3 семействами шрифтов, не более 2–3 начертаний (weights) для каждого (каждое дополнительное начертание — это отдельный запрос).
- [ ] Используется только формат WOFF2 (минимальный размер, универсальная поддержка — пропусти WOFF/TTF/EOT).
- [ ] Шрифты размещаются на собственном сервере (self-hosted), когда это возможно (сторонние CDN для шрифтов добавляют лишние DNS + TCP + TLS транзакции).
- [ ] Шрифты, критичные для LCP, предзагружены: `<link rel="preload" as="font" type="font/woff2" crossorigin>`.
- [ ] Используется `font-display: swap` (или `optional` для некритичных), чтобы избежать блокировки рендеринга из-за FOIT (исчезновения текста при загрузке).
- [ ] Шрифты разбиты на подмножества (subsetted) через `unicode-range`, чтобы поставлять только те символы, которые нужны на каждой конкретной странице.
- [ ] Рассмотри использование вариативных шрифтов, если требуется много начертаний/стилей (один файл заменяет множество).
- [ ] Метрики резервных шрифтов скорректированы с помощью `size-adjust`, `ascent-override`, `descent-override`, чтобы уменьшить CLS при переключении шрифтов.
- [ ] Сначала рассмотри стек системных шрифтов перед добавлением любого кастомного шрифта.

### Сеть (Network)
- [ ] Статические ресурсы кэшируются с долгим временем жизни `max-age` + хешированием контента в имени файла.
- [ ] Ответы API кэшируются там, где это уместно (`Cache-Control`).
- [ ] Включен протокол HTTP/2 или HTTP/3.
- [ ] Настроено предварительное подключение (`<link rel="preconnect">`) для известных сторонних доменов.
- [ ] Используется `fetchpriority` для критически важных ресурсов, отличных от изображений (например, ключевые элементы `<link rel="preload">`, скрипты `<script>` выше сгиба) — не только на тегах `<img>`.
- [ ] Нет лишних перенаправлений (redirects).

### Рендеринг
- [ ] Отсутствует перерасчет макета (layout thrashing) / принудительные синхронные макеты.
- [ ] Анимации используют только свойства `transform` и `opacity` (ускоряются графическим процессором GPU).
- [ ] Длинные списки используют виртуализацию (например, `react-window`).
- [ ] Нет лишних полных перерисовок страницы.
- [ ] Секции вне зоны видимости экрана используют свойство `content-visibility: auto` совместно с `contain-intrinsic-size` для пропуска разметки/отрисовки невидимых областей.
- [ ] Нет обработчиков событий `unload` и отсутствует заголовок `Cache-Control: no-store` в ответах HTML — это сохраняет доступность кэша назад-вперед (bfcache).

## Чеклист для бэкенда

### База данных
- [ ] Отсутствуют шаблоны запросов N+1 (используй eager loading / соединения JOIN).
- [ ] Запросы имеют соответствующие индексы.
- [ ] Конечные точки списков используют пагинацию (никогда не выполняй `SELECT * FROM table`).
- [ ] Настроен пул соединений (connection pooling).
- [ ] Включено логирование медленных запросов.

### API
- [ ] Время ответа < 200мс (p95).
- [ ] Нет тяжелых синхронных вычислений в обработчиках запросов.
- [ ] Используются массовые (bulk) операции вместо циклов из индивидуальных вызовов.
- [ ] Включено сжатие ответов (gzip/brotli).
- [ ] Настроено соответствующее кэширование (in-memory, Redis, CDN).

### Инфраструктура
- [ ] Используется CDN для статических ресурсов.
- [ ] Сервер расположен близко к пользователям (или используется развертывание на границе — edge deployment).
- [ ] Настроено горизонтальное масштабирование (при необходимости).
- [ ] Настроена конечная точка проверки здоровья (health check) для балансировщика нагрузки.

## Команды измерения

### Полевые данные INP и рабочий процесс DevTools

1. **Сначала проверяй полевые данные (field data)** — изучи [CrUX Vis](https://developer.chrome.com/docs/crux/vis) или данные вашей RUM-системы для оценки INP реальных пользователей перед началом оптимизации.
2. **Определи медленные взаимодействия** — открой DevTools → панель Performance → начни запись и повзаимодействуй со страницей; ищи длинные задачи (long tasks), вызванные кликами или нажатиями клавиш.
3. **Тестируй на Android-устройствах среднего уровня** — проблемы с INP часто проявляются только на медленном оборудовании; используй реальное устройство или троттлинг процессора в DevTools (замедление в 4–6 раз).

```bash
# Lighthouse CLI
npx lighthouse https://localhost:3000 --output json --output-path ./report.json

# Анализ бандла
npx webpack-bundle-analyzer stats.json
# или для Vite:
npx vite-bundle-visualizer

# Проверка размера бандла
npx bundlesize

# Отслеживание Web Vitals в коде
import { onLCP, onINP, onCLS } from 'web-vitals';
onLCP(console.log);
onINP(console.log);
onCLS(console.log);

# INP с детализацией на уровне взаимодействий (attribution build)
import { onINP } from 'web-vitals/attribution';
onINP(({ value, attribution }) => {
  const { interactionTarget, inputDelay, processingDuration, presentationDelay } = attribution;
  console.log({ value, interactionTarget, inputDelay, processingDuration, presentationDelay });
});
```

## Распространенные антипаттерны

| Антипаттерн | Влияние | Решение |
|---|---|---|
| Запросы N+1 | Линейный рост нагрузки на БД | Используй JOIN, инклюды (includes) или пакетную загрузку |
| Неограниченные запросы | Исчерпание памяти, тайм-ауты | Всегда используй пагинацию, добавляй LIMIT |
| Отсутствие индексов | Медленное чтение при росте данных | Добавляй индексы для столбцов фильтрации/сортировки |
| Layout thrashing | Подергивания интерфейса, пропущенные кадры | Пакетно считывай DOM, затем пакетно записывай изменения |
| Неоптимизированные изображения | Медленный LCP, трата трафика | Используй WebP, адаптивные размеры, ленивую загрузку |
| Крупные бандлы | Долгое время до интерактивности (TTI) | Разделяй код, используй tree shaking, проверяй зависимости |
| Блокировка главного потока | Низкий INP, неотзывчивый UI | Разбивай длинные задачи через `scheduler.yield()` / `yieldToMain`, выноси вычисления в Web Workers |
| Утечки памяти | Рост потребления памяти, падение приложения | Очищай слушатели событий, интервалы и ссылки на объекты |
