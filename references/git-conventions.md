## Правила именования веток

Имя ветки должно быть лаконичным, написанным в нижнем регистре (kebab-case) и отражать суть изменений.

### Шаблон имени ветки
`[тип]/[краткое-описание-английскими-буквами]`

### Допустимые типы веток:
- `feat` — новая функциональность (фича)
- `fix` — исправление багов
- `docs` — изменения в документации
- `style` — правки форматирования, стилей, отсутствие изменений в логике кода
- `refactor` — рефакторинг кода (без изменения поведения и добавления фич)
- `test` — добавление или изменение тестов
- `chore` — рутинные задачи, обновление зависимостей, сборка и т. д.

### Примеры:
- `feat/user-auth-flow`
- `fix/login-button-spacing`
- `docs/add-api-endpoints`
- `refactor/clean-database-queries`
- `test/unit-tests-user-model`

## Формат коммитов (Conventional Commits)

Каждое сообщение коммита должно соответствовать спецификации **Conventional Commits**. Это позволяет автоматически генерировать changelog и упрощает чтение истории проекта.

### Структура коммита:
```
<тип>(<область>): <краткое описание на английском>

[необязательное тело коммита с подробным описанием]

[необязательный футер со ссылками на задачи]
```

### Допустимые типы коммитов:
- `feat` — добавление новой фичи.
- `fix` — исправление бага.
- `docs` — изменение документации.
- `style` — форматирование, пропущенные точки с запятой и т. д. (код приложения не меняется).
- `refactor` — рефакторинг кода, не изменяющий логику работы.
- `perf` — изменения, направленные на улучшение производительности.
- `test` — добавление или исправление тестов.
- `build` — изменения в системе сборки или внешних зависимостях.
- `ci` — изменения в конфигурационных файлах CI/CD.
- `chore` — другие изменения, не затрагивающие исходный код приложения.
- `revert` — откат предыдущего коммита.

### Правила написания описания:
1. Пиши описание на **английском языке**.
2. Используй повелительное наклонение в настоящем времени (`add user validation`, а не `added user validation` или `adds user validation`).
3. Начинай описание с маленькой буквы.
4. Не ставь точку в конце сообщения коммита.
5. Длина первой строки не должна превышать 72 символа.

### Примеры коммитов:
```
feat(auth): add google oauth provider
```
```
fix(ui): resolve layout shift on mobile navigation dashboard
```
```
docs(readme): update deployment instructions for staging environment
```

### Breaking Changes (Ломающие изменения)
Если коммит содержит ломающие изменения, добавь восклицательный знак `!` перед двоеточием или текст `BREAKING CHANGE:` в начале тела/футера:
```
feat(api)!: remove deprecated v1 endpoints
```
Или:
```
refactor(database): drop legacy user tables

BREAKING CHANGE: The legacy tables are deleted. Run migrations before starting the app.
```

## Атомарные коммиты

- **Один коммит — одна логическая задача.** Не смешивай рефакторинг, исправление опечатки и новую фичу в одном коммите.
- **Рабочее состояние.** Каждый коммит в истории должен быть компилируемым и проходить базовые тесты. Не коммить полурабочий код с синтаксическими ошибками.

## Правила оформления Пул-реквестов (PR)

### Имя пул-реквеста
Название PR должно соответствовать тому же формату Conventional Commits, что и коммиты:
`feat(auth): implement keycloak authentication`

### Шаблон описания PR:
```markdown
## Описание изменений
Кратко расскажи, что именно было сделано и почему.

## Как тестировать
Инструкции для ревьюера, чтобы проверить твою работу.

## Чеклист перед отправкой:
- [ ] Код компилируется без ошибок и предупреждений.
- [ ] Линтер и тесты проходят локально (`npm run lint` и `npm test`).
- [ ] Изменения проверены на адаптивность и доступность.
- [ ] Нет временных логов или закомментированного кода.
```

## Чеклист для агента

Когда ты (ИИ-агент) готовишь изменения для коммита или отправки пул-реквеста, строго следуй этим шагам:

- [ ] **Проверь статус файлов:** Убедись, что в стейджинг добавлены только те файлы, которые относятся к решаемой задаче.
- [ ] **Убери лишнее:** Удали временные файлы, заглушки, `console.log` или закомментированный код, который ты добавил в процессе отладки.
- [ ] **Проверь линтинг и тесты:** Запусти сборку проекта и тесты. Не создавай коммиты, если сборка или линтер выдают ошибки.
- [ ] **Выбери правильное имя ветки:** Если ты создаешь новую ветку, следуй шаблону `тип/описание`.
- [ ] **Сформируй сообщение коммита:** Строго следуй спецификации Conventional Commits на английском языке. Используй повелительное наклонение.
- [ ] **Сохраняй коммиты атомарными:** Если твои изменения затрагивают несколько независимых фич, разбей их на отдельные коммиты.
