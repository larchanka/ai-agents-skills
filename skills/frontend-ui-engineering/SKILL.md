# Разработка интерфейсов (Frontend UI Engineering)

## Обзор

Создавай веб-интерфейсы промышленного качества, которые доступны для пользователей (accessible), производительны и визуально отполированы. Цель состоит в том, чтобы UI выглядел так, будто его разработал опытный инженер с хорошим вкусом в топовой компании, а не сгенерировала нейросеть. Это означает строгое следование дизайн-системе, надлежащую поддержку доступности, продуманные паттерны взаимодействия и отсутствие типичной «шаблонной ИИ-эстетики».

## Когда использовать

- Создание новых UI-компонентов или страниц
- Изменение существующих интерфейсов, с которыми взаимодействуют пользователи
- Реализация адаптивных макетов (responsive layouts)
- Добавление интерактивности или логики управления состоянием
- Исправление визуальных дефектов или проблем с юзабилити (UX)

## Архитектура компонентов

### Структура папок

Размещай все файлы, относящиеся к одному компоненту, в одной папке:

```
src/components/
  TaskList/
    TaskList.tsx          # Реализация компонента
    TaskList.test.tsx     # Тесты
    TaskList.stories.tsx  # Истории Storybook (при наличии)
    use-task-list.ts      # Кастомный хук (при сложной логике состояния)
    types.ts              # Специфичные для компонента типы (при необходимости)
```

### Паттерны компонентов

**Предпочитай композицию жесткой конфигурации через пропсы:**

```tsx
// Хорошо: Композиция
<Card>
  <CardHeader>
    <CardTitle>Задачи</CardTitle>
  </CardHeader>
  <CardBody>
    <TaskList tasks={tasks} />
  </CardBody>
</Card>

// Избегай: Избыточная конфигурация через пропсы
<Card
  title="Задачи"
  headerVariant="large"
  bodyPadding="md"
  content={<TaskList tasks={tasks} />}
/>
```

**Держи компоненты сфокусированными на одной задаче:**

```tsx
// Хорошо: Компонент решает одну задачу
export function TaskItem({ task, onToggle, onDelete }: TaskItemProps) {
  return (
    <li className="flex items-center gap-3 p-3">
      <Checkbox checked={task.done} onChange={() => onToggle(task.id)} />
      <span className={task.done ? 'line-through text-muted' : ''}>{task.title}</span>
      <Button variant="ghost" size="sm" onClick={() => onDelete(task.id)}>
        <TrashIcon />
      </Button>
    </li>
  );
}
```

**Разделяй получение данных и презентационную логику:**

```tsx
// Контейнер: отвечает за данные
export function TaskListContainer() {
  const { tasks, isLoading, error } = useTasks();

  if (isLoading) return <TaskListSkeleton />;
  if (error) return <ErrorState message="Не удалось загрузить задачи" retry={refetch} />;
  if (tasks.length === 0) return <EmptyState message="Задач пока нет" />;

  return <TaskList tasks={tasks} />;
}

// Презентация: отвечает за отрисовку
export function TaskList({ tasks }: { tasks: Task[] }) {
  return (
    <ul role="list" className="divide-y">
      {tasks.map(task => <TaskItem key={task.id} task={task} />)}
    </ul>
  );
}
```

## Управление состоянием (State Management)

**Выбирай самый простой подход, который решает задачу:**

```
Локальное состояние (useState)     → Специфичное состояние UI одного компонента
Поднятое состояние (Lifted state)  → Общее состояние для 2-3 соседних компонентов
Контекст (Context)                 → Тема, авторизация, локаль (частое чтение, редкая запись)
Состояние в URL (searchParams)     → Фильтры, пагинация, шаринг ссылок на состояние UI
Состояние сервера (React Query)    → Удаленные данные с кэшированием
Глобальный стор (Zustand, Redux)   → Сложное клиентское состояние на уровне всего приложения
```

**Избегай передачи пропсов (prop drilling) глубже чем на 3 уровня.** Если ты передаешь пропсы через компоненты, которые их не используют, внедри контекст или перепроектируй дерево компонентов.

## Соблюдение дизайн-системы

### Избегай шаблонной «ИИ-эстетики»

Сгенерированные ИИ интерфейсы имеют узнаваемые шаблоны. Избегай их полностью:

| Шаблон ИИ по умолчанию | Почему это плохо | Промышленный стандарт качества |
|---|---|---|
| Все элементы фиолетовые/индиго | Модели выбирают визуально «безопасные» палитры, из-за чего все приложения выглядят одинаково | Используй реальную цветовую палитру проекта |
| Избыточные градиенты | Градиенты добавляют визуальный шум и часто конфликтуют с дизайн-системами | Используй плоские или деликатные градиенты, соответствующие дизайн-системе |
| Максимальное скругление углов (`rounded-2xl`) | Чрезмерное скругление выглядит несерьезно и игнорирует иерархию радиусов в реальных дизайнах | Используй единообразные радиусы скругления из дизайн-системы |
| Однотипные главные экраны (Hero) | Шаблонный макет без связи с реальным контентом или потребностями пользователя | Разметка на основе контента и реальных задач страницы |
| Текст-рыба (Lorem Ipsum) | Заглушки скрывают проблемы макета (перенос длинных слов, переполнение блоков) | Используй реалистичный рыботекст или тестовые данные |
| Избыточные отступы (padding) везде | Одинаковые щедрые отступы ломают визуальную иерархию и крадут полезную площадь экрана | Используй единую шкалу отступов |
| Бесконечные сетки из карточек | Сетки из карточек — простой способ верстки, игнорирующий приоритеты информации | Макеты, спроектированные под конкретные сценарии |
| Тяжелые, навязчивые тени | Наслоение теней перегружает интерфейс и замедляет рендеринг на слабых устройствах | Используй незаметные тени или откажись от них вовсе, если дизайн-система не требует иного |

### Отступы и макет

Используй последовательную шкалу отступов. Не выдумывай значения:

```css
/* Используй шкалу: шаг в 0.25rem (или то, что принято в проекте) */
/* Хорошо */  padding: 1rem;      /* 16px */
/* Хорошо */  gap: 0.75rem;       /* 12px */
/* Плохо */   padding: 13px;      /* Выбивается из сетки */
/* Плохо */   margin-top: 2.3rem; /* Выбивается из сетки */
```

### Типографика

Уважай иерархию шрифтов:

```
h1 → Название страницы (один элемент на страницу)
h2 → Заголовок раздела
h3 → Заголовок подраздела
body → Основной текст
small → Вспомогательный текст
```

Не пропускай уровни заголовков. Не используй стили заголовков для контента, не являющегося заголовком.

### Цвет

- Используй семантические токены цвета: `text-primary`, `bg-surface`, `border-default` — а не «сырые» hex-значения.
- Обеспечь достаточный контраст (4.5:1 для обычного текста, 3:1 для крупного текста).
- Не полагайся исключительно на цвет для передачи информации (используй также иконки, текст или узоры).

## Доступность (Accessibility по WCAG 2.1 AA)

Каждый компонент должен соответствовать этим стандартам:

### Клавиатурная навигация

```tsx
// Каждый интерактивный элемент должен быть доступен с клавиатуры
<button onClick={handleClick}>Нажми меня</button>        // ✓ Фокусируется по умолчанию
<div onClick={handleClick}>Нажми меня</div>               // ✗ Не фокусируется клавиатурой
<div role="button" tabIndex={0} onClick={handleClick}    // ✓ Допустимо, но лучше использовать <button>
     onKeyDown={e => {
       if (e.key === 'Enter') handleClick();
       if (e.key === ' ') e.preventDefault();
     }}
     onKeyUp={e => {
       if (e.key === ' ') handleClick();
     }}>
  Нажми меня
</div>
```

### Метки ARIA

```tsx
// Подписывай интерактивные элементы, не имеющие видимого текста
<button aria-label="Закрыть диалог"><XIcon /></button>

// Подписывай поля ввода в формах
<label htmlFor="email">Email</label>
<input id="email" type="email" />

// Или используй aria-label, когда видимая подпись отсутствует
<input aria-label="Поиск задач" type="search" />
```

### Управление фокусом

```tsx
// Переноси фокус при динамическом изменении контента
function Dialog({ isOpen, onClose }: DialogProps) {
  const closeRef = useRef<HTMLButtonElement>(null);

  useEffect(() => {
    if (isOpen) closeRef.current?.focus();
  }, [isOpen]);

  // Удерживай фокус (focus trap) внутри диалогового окна, пока оно открыто
  return (
    <dialog open={isOpen}>
      <button ref={closeRef} onClick={onClose}>Закрыть</button>
      {/* Контент диалога */}
    </dialog>
  );
}
```

### Информативные состояния пустых списков и ошибок

```tsx
// Не показывай пустые белые экраны
function TaskList({ tasks }: { tasks: Task[] }) {
  if (tasks.length === 0) {
    return (
      <div role="status" className="text-center py-12">
        <TasksEmptyIcon className="mx-auto h-12 w-12 text-muted" />
        <h3 className="mt-2 text-sm font-medium">Нет задач</h3>
        <p className="mt-1 text-sm text-muted">Начни работу с создания первой задачи.</p>
        <Button className="mt-4" onClick={onCreateTask}>Создать задачу</Button>
      </div>
    );
  }

  return <ul role="list">...</ul>;
}
```

## Адаптивный дизайн (Responsive Design)

Проектируй сначала для мобильных устройств (mobile first), затем расширяй интерфейс для больших экранов:

```tsx
// Tailwind: адаптивность mobile-first
<div className="
  grid grid-cols-1      /* Мобильные: одна колонка */
  sm:grid-cols-2        /* Планшеты: две колонки */
  lg:grid-cols-3        /* Десктопы: три колонки */
  gap-4
">
```

Тестируй на этих брейкпоинтах: 320px, 768px, 1024px, 1440px.

## Индикация загрузки и переходы

```tsx
// Скелетоны для загрузки контента (а не бесконечные спиннеры)
function TaskListSkeleton() {
  return (
    <div className="space-y-3" aria-busy="true" aria-label="Загрузка задач">
      {Array.from({ length: 3 }).map((_, i) => (
        <div key={i} className="h-12 bg-muted animate-pulse rounded" />
      ))}
    </div>
  );
}

// Оптимистичные обновления (optimistic updates) для ощущения мгновенной работы
function useToggleTask() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: toggleTask,
    onMutate: async (taskId) => {
      await queryClient.cancelQueries({ queryKey: ['tasks'] });
      const previous = queryClient.getQueryData(['tasks']);

      queryClient.setQueryData(['tasks'], (old: Task[]) =>
        old.map(t => t.id === taskId ? { ...t, done: !t.done } : t)
      );

      return { previous };
    },
    onError: (_err, _taskId, context) => {
      queryClient.setQueryData(['tasks'], context?.previous);
    },
  });
}
```

## Распространенные оправдания

| Оправдание | Реальность |
|---|---|
| «Доступность (A11y) — это опционально» | Это юридическое требование во многих странах и важный стандарт профессионального качества кода. |
| «Мы сделаем его адаптивным позже» | Внедрение адаптивности в готовый интерфейс в 3 раза сложнее, чем разработка с адаптивным подходом с самого начала. |
| «Дизайн еще не утвержден, поэтому я пока не буду стилизовать UI» | Используй дефолтные стили дизайн-системы. Нестилизованный UI создает ощущение сломанного приложения у рецензентов. |
| «Это всего лишь прототип» | Прототипы часто становятся основой продакшн-кода. Сразу закладывай правильный фундамент. |
| «Временный ИИ-стиль выглядит нормально» | Это сигнализирует о низком качестве разработки. Сразу используй реальную дизайн-систему проекта. |

## Красные флаги

- Компоненты объемом более 200 строк (разделяй их).
- Инлайн-стили (inline styles) или произвольные пиксельные значения вместо токенов дизайн-системы.
- Отсутствие экранов загрузки, ошибок или пустых состояний.
- Отсутствие проверки навигации с клавиатуры.
- Использование цвета как единственного индикатора состояния (например, красная/зеленая точка без иконки или поясняющего текста).
- Типичный «вид сгенерированного ИИ шаблона» (фиолетовые градиенты, огромные скругления, стоковая разметка).

## Проверка

После завершения верстки интерфейса убедись, что:

- [ ] Компонент рендерится без ошибок в консоли.
- [ ] Все интерактивные элементы доступны с клавиатуры (пройдись клавишей Tab по всей странице).
- [ ] Программа чтения с экрана (screen reader) может корректно передать структуру и контент страницы.
- [ ] Адаптивность проверена и работает при ширине: 320px, 768px, 1024px, 1440px.
- [ ] Отрисовка состояний загрузки, ошибок и пустого контента протестирована.
- [ ] Оформление полностью соответствует дизайн-системе проекта (отступы, цвета, шрифты).
- [ ] Отсутствуют предупреждения доступности (accessibility warnings) в консоли DevTools или axe-core.
