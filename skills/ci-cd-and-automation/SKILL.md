# CI/CD и автоматизация

## Обзор

Автоматизируй контроли качества (quality gates), чтобы ни одно изменение не попадало в продакшн без прохождения тестов, линтинга, проверки типов и сборки. CI/CD — это механизм принудительного соблюдения для любого другого навыка: он выявляет то, что упускают люди и агенты, и делает это последовательно при каждом отдельном изменении.

**Сдвиг влево (Shift Left):** Выявляй проблемы как можно раньше на конвейере. Баг, обнаруженный при линтинге, стоит минут; тот же баг, обнаруженный в продакшне, стоит часов. Переноси проверки выше по потоку: статический анализ перед тестами, тесты перед стейджингом, стейджинг перед продакшном.

**Быстрее — значит безопаснее:** Небольшие пакеты изменений и более частые релизы снижают риск, а не увеличивают его. Развертывание с 3 изменениями отлаживать проще, чем с 30. Частые релизы укрепляют уверенность в самом процессе выпуска.

## Когда использовать

- Настройка конвейера CI для нового проекта
- Добавление или изменение автоматических проверок
- Настройка конвейеров развертывания
- Когда изменение должно запускать автоматическую проверку
- Отладка сбоев CI

## Конвейер контроля качества (Quality Gate Pipeline)

Каждое изменение проходит через эти фильтры перед слиянием (merge):

```
Открытие Pull Request
    │
    ▼
┌─────────────────┐
│ ЛИНТИНГ (LINT)  │  eslint, prettier
│   ↓ успех       │
│ ПРОВЕРКА ТИПОВ  │  tsc --noEmit
│   ↓ успех       │
│ ЮНИТ-ТЕСТЫ      │  jest/vitest
│   ↓ успех       │
│ СБОРКА (BUILD)  │  npm run build
│   ↓ успех       │
│ ИНТЕГРАЦИЯ      │  тесты API/БД
│   ↓ успех       │
│ E2E (опционально)│ Playwright/Cypress
│   ↓ успех       │
│ АУДИТ БЕЗОПАСН. │  npm audit
│   ↓ успех       │
│ РАЗМЕР БАНДЛА   │  проверка bundlesize
└─────────────────┘
    │
    ▼
 Готов к ревью
```

**Ни один фильтр нельзя пропустить.** Если линтинг не проходит, исправь линтер — не отключай правило. Если тест падает, исправь код — не пропускай тест.

## GitHub Actions Конфигурация

### Базовый конвейер CI

```yaml
# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Lint
        run: npm run lint

      - name: Type check
        run: npx tsc --noEmit

      - name: Test
        run: npm test -- --coverage

      - name: Build
        run: npm run build

      - name: Security audit
        run: npm audit --audit-level=high
```

### С интеграционными тестами базы данных

```yaml
  integration:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_DB: testdb
          POSTGRES_USER: ci_user
          POSTGRES_PASSWORD: ${{ secrets.CI_DB_PASSWORD }}
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'
      - run: npm ci
      - name: Run migrations
        run: npx prisma migrate deploy
        env:
          DATABASE_URL: postgresql://ci_user:${{ secrets.CI_DB_PASSWORD }}@localhost:5432/testdb
      - name: Integration tests
        run: npm run test:integration
        env:
          DATABASE_URL: postgresql://ci_user:${{ secrets.CI_DB_PASSWORD }}@localhost:5432/testdb
```

> **Примечание:** Даже для тестовых баз данных, используемых только в CI, используй GitHub Secrets для хранения учетных данных вместо жесткого кодирования значений. Это вырабатывает хорошие привычки и предотвращает случайное повторное использование тестовых доступов в других контекстах.

### Тесты E2E

```yaml
  e2e:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'
      - run: npm ci
      - name: Install Playwright
        run: npx playwright install --with-deps chromium
      - name: Build
        run: npm run build
      - name: Run E2E tests
        run: npx playwright test
      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: playwright-report
          path: playwright-report/
```

## Передача отчетов о сбоях CI обратно агентам

Сила CI при работе с ИИ-агентами заключается в цикле обратной связи. Когда CI дает сбой:

```
Сбой CI
    │
    ▼
Скопируй лог ошибки сбоя
    │
    ▼
Передай его агенту:
"Конвейер CI завершился сбоем со следующей ошибкой:
[вставь конкретную ошибку]
Исправь проблему и проверь ее локально перед повторной отправкой."
    │
    ▼
Агент исправляет → отправляет (push) → CI запускается снова
```

**Ключевые шаблоны действий:**

```
Сбой линтинга -> Агент запускает `npm run lint --fix` и коммитит изменения
Ошибка типов   -> Агент считывает место ошибки и исправляет тип
Сбой теста     -> Агент следует навыку debugging-and-error-recovery (отладка и восстановление после ошибок)
Ошибка сборки  -> Агент проверяет конфигурацию и зависимости
```

## Стратегии развертывания

### Предварительное развертывание (Preview Deployments)

Каждый PR получает предварительное развертывание (preview deployment) для ручного тестирования:

```yaml
# Развертывание превью при PR (Vercel/Netlify/и т.д.)
deploy-preview:
  runs-on: ubuntu-latest
  if: github.event_name == 'pull_request'
  steps:
    - uses: actions/checkout@v4
    - name: Deploy preview
      run: npx vercel --token=${{ secrets.VERCEL_TOKEN }}
```

### Флаги фич (Feature Flags)

Флаги фич отделяют развертывание от релиза. Разворачивай незавершенные или рискованные фичи под флагами, чтобы ты мог:

- **Поставлять код без его включения.** Сливай изменения в ветку main на ранних этапах, включай фичу, когда она будет готова.
- **Откатывать изменения без повторного развертывания.** Просто отключи флаг вместо отката коммитов кода.
- **Проводить канареечные релизы (Canary).** Включай фичу для 1% пользователей, затем для 10%, затем для 100%.
- **Проводить A/B-тестирование.** Сравнивай поведение системы с включенной и выключенной фичей.

```typescript
// Простой шаблон флага фичи
if (featureFlags.isEnabled('new-checkout-flow', { userId })) {
  return renderNewCheckout();
}
return renderLegacyCheckout();
```

**Жизненный цикл флага:** Создай -> Включи для тестирования -> Запусти канареечный релиз -> Полный релиз -> Удали флаг и мертвый код. Флаги, которые живут вечно, становятся техническим долгом — устанавливай дату очистки при их создании.

### Поэтапное развертывание (Staged Rollouts)

```
Слияние PR в ветку main
    │
    ▼
 Развертывание на Staging (автоматически)
    │ Ручная проверка
    ▼
 Развертывание на Production (ручной запуск или авто после staging)
    │
    ▼
 Мониторинг ошибок (15-минутное окно)
    │
    ├── Обнаружены ошибки → Откат (Rollback)
    └── Ошибок нет → Готово
```

### План отката (Rollback Plan)

Каждое развертывание должно быть обратимым:

```yaml
# Рабочий процесс ручного отката
name: Rollback
on:
  workflow_dispatch:
    inputs:
      version:
        description: 'Версия для отката'
        required: true

jobs:
  rollback:
    runs-on: ubuntu-latest
    steps:
      - name: Rollback deployment
        run: |
          # Развертывание указанной предыдущей версии
          npx vercel rollback ${{ inputs.version }}
```

## Управление окружением

```
.env.example        → Фиксируется в репозитории (шаблон для разработчиков)
.env                → НЕ фиксируется в репозитории (локальная разработка)
.env.test           → Фиксируется в репозитории (тестовое окружение, без реальных секретов)
Секреты CI          → Хранятся в GitHub Secrets / хранилище (vault)
Секреты Production  → Хранятся на платформе развертывания / хранилище (vault)
```

CI никогда не должен иметь доступ к секретам продакшна. Используй отдельные секреты для тестирования в CI.

## Автоматизация помимо CI

### Dependabot / Renovate

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule:
      interval: weekly
    open-pull-requests-limit: 5
```

### Роль дежурного по сборке (Build Cop)

Назначь ответственного за то, чтобы CI оставался «зеленым». При сбое сборки задача Build Cop — исправить или откатить изменения, а не задача того человека, чьи правки вызвали сбой. Это предотвращает накопление сломанных сборок, когда каждый думает, что проблему исправит кто-то другой.

### Проверки PR (PR Checks)

- **Обязательные обзоры:** Как минимум 1 одобрение перед слиянием
- **Обязательные проверки статуса:** CI должен проходить успешно перед слиянием
- **Защита веток:** Запрет force-push в ветку main
- **Автослияние (Auto-merge):** Если все проверки пройдены и получено одобрение, слияние происходит автоматически

## Оптимизация CI

Когда время выполнения конвейера превышает 10 минут, применяй следующие стратегии в порядке их эффективности:

```
Медленный конвейер CI?
├── Кэшируй зависимости
│   └── Используй actions/cache или опцию кэширования setup-node для node_modules
├── Запускай задачи параллельно
│   └── Раздели линтинг, проверку типов, тесты и сборку на отдельные параллельные задачи
├── Запускай только то, что изменилось
│   └── Используй фильтры путей, чтобы пропускать нерелевантные задачи (например, e2e при обновлении только документации)
├── Используй матрицы сборки (matrix builds)
│   └── Распределяй наборы тестов между несколькими исполнителями (runners)
├── Оптимизируй тестовый набор
│   └── Удали медленные тесты с критического пути выполнения, запуская их по расписанию
└── Используй более производительные исполнители (runners)
    └── Используй более мощные runners от GitHub или собственные (self-hosted) для ресурсоемких сборок
```

**Пример: кэширование и параллелизм**
```yaml
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22', cache: 'npm' }
      - run: npm ci
      - run: npm run lint

  typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22', cache: 'npm' }
      - run: npm ci
      - run: npx tsc --noEmit

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22', cache: 'npm' }
      - run: npm ci
      - run: npm test -- --coverage
```

## Распространенные оправдания

| Оправдание | Реальность |
|---|---|
| «CI работает слишком медленно» | Оптимизируй конвейер (см. раздел «Оптимизация CI» ниже), а не пропускай его. 5-минутный конвейер предотвращает часы отладки. |
| «Это изменение тривиально, пропустим CI» | Тривиальные изменения ломают сборки. К тому же, для простых изменений CI отрабатывает очень быстро. |
| «Тест нестабилен (flaky), просто перезапусти его» | Нестабильные тесты маскируют реальные баги и тратят время команды. Исправь нестабильность теста. |
| «Мы добавим CI позже» | Проекты без CI накапливают сломанные состояния. Настраивай его в первый же день. |
| «Ручного тестирования достаточно» | Ручное тестирование не масштабируется и не является воспроизводимым. Автоматизируй все, что возможно. |

## Красные флаги

- Отсутствие конвейера CI в проекте
- Игнорирование или сокрытие сбоев CI
- Отключение тестов в CI ради успешного прохождения конвейера
- Развертывание на продакшн без проверки на стейджинге
- Отсутствие механизма отката изменений (rollback)
- Хранение секретов в коде или в конфигурационных файлах CI (вместо менеджера секретов)
- Длительное время выполнения CI без каких-либо попыток оптимизации

## Проверка

После настройки или изменения CI:

- [ ] Все контроли качества на месте (линтинг, проверка типов, тесты, сборка, аудит)
- [ ] Конвейер запускается при каждом PR и пуше в ветку main
- [ ] Сбои блокируют слияние (настроена защита веток)
- [ ] Результаты CI передаются обратно в цикл разработки
- [ ] Секреты хранятся в менеджере секретов, а не в коде
- [ ] Процесс развертывания имеет механизм отката (rollback)
- [ ] Время выполнения конвейера для набора тестов составляет менее 10 минут
