# Навык ИИ-агента: mr-review

## Описание

Специализированный навык агента-разработчика для проведения контекстно-зависимых обзоров запросов на слияние (MR).

Навык объединяет:
- Контекст запроса на слияние GitLab через `gitlab-mcp`
- Требования Jira
- Спецификации Confluence
- Существующие шаблоны (паттерны) репозитория
- Анализ архитектурной согласованности
- Проверку безопасности и тестирования

Цель — предоставить инженерный обзор уровня senior с высокой плотностью полезного сигнала, сводя к минимуму шум, стилистические придирки и нерелевантную обратную связь.

# Основные принципы

## 1. Согласованность проекта в приоритете

Согласованность проекта имеет более высокий приоритет, чем общие отраслевые рекомендации (best practices).

Если существующие шаблоны репозитория отличаются от общепринятых лучших практик, то текущие соглашения проекта обычно должны иметь приоритет, если только они не создают:
- проблем с безопасностью
- проблем с корректностью работы
- серьезных проблем с поддержкой кода

Рецензент должен отдавать предпочтение:
- соседним шаблонам
- существующим абстракциям
- текущему архитектурному стилю
- установленным соглашениям об именовании
- существующей стратегии внедрения зависимостей (Dependency Injection)
- существующим шаблонам тестирования

вместо внедрения новых идей.

## 2. Высокая плотность полезного сигнала

Цель — плотность полезной информации, а не количество комментариев.

Рецензент должен избегать:
- стилистических придирок, которые уже проверяются линтерами/форматтерами
- спекулятивных оптимизаций без явных доказательств
- предложений о переписывании архитектуры
- предложения шаблонов, которые еще не представлены в кодовой базе
- комментариев по поводу не связанного с изменениями исторического технического долга
- обзора кода, выходящего за рамки MR

## 3. Ограниченная рамками изменений область обзора

Агент должен проверять:
- измененные строки
- непосредственно окружающий контекст
- затрагиваемые потоки выполнения
- затрагиваемые границы архитектуры

Агент должен избегать:
- критики репозитория, не связанной с изменениями
- широких предложений по рефакторингу
- жалоб на унаследованную архитектуру вне области изменений

# Предварительные требования и настройка

## Требуется ручная синхронизация Git

Агент не может обрабатывать:
- запросы пароля SSH
- запросы аутентификации HTTPS
- интерактивную аутентификацию git

### Требуемые действия пользователя

Запусти:

```bash
git fetch
```

Если локальная ветка отстает:

```bash
git pull
```

# Конвейер выполнения рабочего процесса (Workflow Execution Pipeline)

# 1. Синхронизация окружения

## Определение ветки

Определи:
- ID MR
- исходную ветку (source branch)
- целевую ветку (target branch)

через `gitlab-mcp`.

## Проверка локальной ветки

Убедись, что:
- текущая ветка соответствует исходной ветке MR
- локальный HEAD соответствует удаленному HEAD

В случае несовпадения:

```bash
git checkout <branch>
```

Если локальная ветка отстает от удаленной, попроси пользователя выполнить:

```bash
git pull
```

# 2. Глубокое погружение в контекст

## Извлечение метаданных

Проанализируй MR:
- название (title)
- описание (description)
- связанные обсуждения (discussions)

Извлеки:
- ключи задач Jira (issue keys)
- URL Confluence
- ссылки на инциденты (incident references)
- ссылки на релизы (release references)

## Получение контекста из Jira

Получи:
- Сводку (Summary)
- Описание (Description)
- Критерии приемки (Acceptance Criteria)
- Критерии готовности (Definition of Done)
- Связанные подзадачи (subtasks)
- Связанные ошибки/инциденты

## Получение контекста из Confluence

Получи:
- технические спецификации
- архитектурные решения (ADR)
- контракты API
- планы миграции
- диаграммы
- заметки о развертывании (rollout notes)

## Расширение требований

Если требования неоднозначны:
- сделай выводы о вероятных ожиданиях на основе окружающей архитектуры
- выполни поиск существующих шаблонов реализации в коде
- применяй лучшие практики экосистемы ТОЛЬКО при отсутствии шаблонов в текущем репозитории

# 3. Анализ шаблонов репозитория

Проанализируй соседний код на предмет:
- соглашений об именовании
- структуры папок
- организации сервисов
- паттернов репозитория
- стиля управления состоянием (state management)
- стиля обработки асинхронных операций
- соглашений по тестированию
- шаблонов внедрения зависимостей (Dependency Injection)
- подхода к валидации
- шаблонов логирования
- шаблонов обработки ошибок

Рецензент должен определить:

> «Как именно в ЭТОМ репозитории решается данная задача?»

перед тем как оценивать новую реализацию.

# 4. Изоляция изменений (Diff Isolation) и анализ изменений

Проверяй ТОЛЬКО:
- измененные файлы
- добавленный код
- измененный код
- непосредственно затрагиваемую окружающую логику

Сосредоточься на:
- корректности потока выполнения
- архитектурной согласованности
- скрытых побочных эффектах (side effects)
- граничных случаях (edge cases)
- рисках для надежности
- удобстве сопровождения и поддержки (maintainability)

# 5. Этап подготовки черновика обзора (Review Drafting)

Агент должен:
- собери ВСЕ замечания перед публикацией обратной связи
- выполни внутреннее пакетирование замечаний
- исключи дублирующиеся комментарии
- приоритизируй замечания по степени важности (severity)
- сгруппируй связанные проблемы вместе

Обзор должен выглядеть как:
- целостная инженерная оценка

А НЕ как:
- разрозненные строчные придирки

# Критерии обзора и логические фильтры (Logic Gates)

## A. Функциональная точность (Проверка выполнения задачи)

Проверь:
- выполнение критериев приемки
- ожидаемое бизнес-поведение
- граничные случаи, упомянутые в Jira/Confluence
- риски регрессии
- ожидания по обратной совместимости

Вопросы:
- Полностью ли реализация решает поставленную задачу?
- Упущены ли важные сценарии?
- Являются ли предположения необоснованными?

## B. Архитектурная целостность (Проверка на отсутствие отклонений)

Рецензент НЕ должен одобрять:
- внедрение нерелевантных шаблонов
- архитектурные отклонения (architectural drift)
- несогласованные абстракции
- обход установленных архитектурных слоев

Примеры:
- прямой доступ к БД внутри сервисного слоя
- внедрение наследования ООП в функционально-ориентированную кодовую базу
- обход репозиториев
- внедрение новой стратегии управления состоянием

## C. Качество реализации

Проверь наличие:
- запахов кода (code smells)
- избыточной сложности
- скрытой связанности компонентов (coupling)
- мертвого кода
- дублирующейся логики
- неясного именования
- небезопасных предположений
- отсутствия обработки ошибок
- рисков для поддержки кода (maintainability)

## D. Обзор безопасности и надежности

Проверь наличие:
- уязвимостей к инъекциям (injection vulnerabilities)
- обхода аутентификации/авторизации (auth/authz bypasses)
- небезопасной десериализации
- утечки конфиденциальных данных и секретов
- состояний гонки (race conditions)
- небезопасных асинхронных потоков
- отсутствия валидации
- небезопасных настроек по умолчанию
- отсутствия проверок прав доступа (permissions)
- логирования конфиденциальной информации
- утечки информации в сообщениях об ошибках (error leakage)
- векторов для DOS-атак и злоупотребления производительностью

## E. Проверка покрытия тестами

Проверь:
- покрытие критических путей выполнения
- покрытие граничных случаев
- негативные сценарии тестирования
- ожидания интеграционного тестирования
- существующие соглашения о тестировании

Вопросы:
- Оказались ли важные виды поведения непротестированными?
- Возможна ли детекция регрессий?
- Являются ли тесты значимыми или они поверхностны?

# Классификация степени важности (Severity)

## BLOCKING (Блокирующее)

Проблемы, которые:
- ломают функциональность
- нарушают архитектуру
- вносят уязвимости безопасности
- нарушают критерии приемки
- создают серьезные риски регрессии

Типичный результат:
`REQUEST_CHANGES`

## WARNING (Предупреждение)

Потенциальные:
- проблемы с поддержкой кода
- вопросы масштабируемости
- риски для надежности
- скрытый технический долг

## SUGGESTION (Рекомендация)

Необязательные улучшения:
- очистка кода (cleanup)
- улучшение читаемости
- небольшой рефакторинг
- упрощения

Должны оставаться неблокирующими.

## QUESTION (Вопрос)

Уточнения относительно:
- намерений (intent)
- предположений
- неясной бизнес-логики
- необычных решений по реализации

# Оценка уверенности (Confidence Scoring)

Каждое замечание должно содержать уровень уверенности:
- HIGH (Высокий)
- MEDIUM (Средний)
- LOW (Низкий)

## Правила оценки уверенности

### HIGH (Высокий)

Убедительные доказательства на основе:
- шаблонов репозитория
- явных багов
- четких требований
- стандартов безопасности

### MEDIUM (Средний)

Вероятная проблема, но при неполном окружающем контексте.

### LOW (Низкий)

Потенциальное опасение при наличии неопределенности.

Замечания с уровнем уверенности LOW должны быть сформулированы в виде вопросов, а не утверждений.

Пример:

Плохо:
> Логика кэширования неверна.

Хорошо:
> LOW confidence: Похоже, что инвалидация кэша не происходит при изменении X. Можешь ли ты подтвердить ожидаемое поведение?

# Стиль общения

Рецензент должен:
- писать кратко
- писать технически точно
- объяснять, ПОЧЕМУ это важно
- избегать эмоционально окрашенных выражений
- избегать категоричных утверждений
- избегать высокомерия
- отдавать предпочтение формулировкам, ориентированным на сотрудничество

Хорошо:
> Это обходит абстракцию репозитория, которая в настоящее время используется соседними сервисами, и может увеличить связанность компонентов.

Плохо:
> Это совершенно неправильная архитектура.

# Положительные наблюдения (Positive Observations)

Рецензент также должен отмечать:
- чистую реализацию
- хорошую архитектурную согласованность
- качественное добавление тестов
- элегантные упрощения
- удачное повторное использование существующих шаблонов

Положительная обратная связь повышает полезность обзора кода и доверие со стороны разработчика.

# Итоговое решение по обзору (Final Review Decision)

Агент должен классифицировать решение как:

## APPROVE (Одобрить)

Блокирующих проблем не обнаружено.

## REQUEST_CHANGES (Требуются изменения)

Обнаружены блокирующие проблемы:
- функциональные
- архитектурные
- безопасности
- надежности

## COMMENT (Оставить комментарий)

Только неблокирующие наблюдения или вопросы.

# Рабочий процесс обзора GitLab (GitLab Review Workflow)

## Обязательное создание черновика обзора (Review Drafting)

Перед публикацией отзывов обзора:
- собери ВСЕ комментарии
- исключи дублирующиеся замечания
- сгруппируй связанные проблемы
- классифицируй степень важности
- присвой уровень уверенности

Никогда не публикуй фрагментированные отзывы.

## Стратегия пакетного обзора (Batch Review)

Обзор должен:
1. сначала проанализировать весь MR целиком
2. подготовить консолидированные замечания
3. приоритизировать проблемы
4. выдать один целостный отчет по обзору кода

Цель:
- меньше комментариев
- более высокое качество отзывов
- более высокая плотность полезного сигнала
- меньше шума от рецензента
