# Ревью кода и контроль качества

## Обзор

Многомерное ревью кода с контрольными точками качества. Каждое изменение должно пройти ревью перед слиянием — без исключений. Проверка проводится по пяти направлениям: корректность, читаемость, архитектура, безопасность и производительность.

**Критерий одобрения:** Одобряй изменение, если оно однозначно улучшает общее состояние кодовой базы, даже если оно не идеально. Идеального кода не существует — цель заключается в постоянном улучшении. Не блокируй изменение только потому, что ты написал бы его иначе. Если оно улучшает проект и соответствует принятым в нем соглашениям, его следует одобрить.

## Когда использовать

- Перед слиянием любого PR или изменения
- После завершения реализации функциональности
- Когда код был написан другим агентом или моделью и требует оценки
- При рефакторинге существующего кода
- После исправления любого бага (проверяй и исправление, и регрессионный тест)

## Пять направлений ревью

Каждое ревью должно оценивать код по следующим направлениям.

### 1. Корректность

Делает ли код то, что заявлено?

- Соответствует ли он спецификации или требованиям задачи?
- Обработаны ли граничные случаи (`null`, пустые значения, граничные диапазоны)?
- Обработаны ли ошибочные сценарии, а не только «счастливый путь»?
- Проходят ли все тесты? Проверяют ли тесты именно то, что нужно?
- Нет ли ошибок типа off-by-one, гонок данных или несогласованности состояния?

### 2. Читаемость и простота

Сможет ли другой инженер (или агент) понять этот код без объяснений автора?

- Являются ли названия понятными и соответствуют ли соглашениям проекта? (Без `temp`, `data`, `result` без контекста.)
- Является ли поток выполнения простым и понятным? (Избегай вложенных тернарных операторов и глубоких цепочек колбэков.)
- Логично ли организован код? (Связанные части сгруппированы, границы модулей понятны.)
- Есть ли слишком «умные» решения, которые стоит упростить?
- **Можно ли решить задачу меньшим количеством строк?** (1000 строк там, где достаточно 100 — это проблема.)
- **Оправдывают ли абстракции свою сложность?** (Не обобщай до появления как минимум третьего сценария использования.)
- Помогли бы комментарии объяснить неочевидные намерения? (Но не комментируй очевидный код.)
- Есть ли следы мертвого кода: неиспользуемые переменные (`_unused`), временные слои совместимости или комментарии вида `// removed`?

### 3. Архитектура

Соответствует ли изменение архитектуре системы?

- Следует ли оно существующим шаблонам или вводит новый? Если новый — оправдано ли это?
- Сохраняются ли чистые границы между модулями?
- Есть ли дублирование кода, которое стоит вынести в общее решение?
- Правильно ли направлены зависимости? (Нет ли циклических зависимостей?)
- Соответствует ли уровень абстракции задаче? (Нет ли переусложнения или чрезмерной связанности?)

### 4. Безопасность

Подробные рекомендации см. в `security-and-hardening`.

Вносит ли изменение уязвимости?

- Валидируется и очищается ли пользовательский ввод?
- Не попадают ли секреты в код, логи и систему контроля версий?
- Проверяется ли аутентификация и авторизация там, где это требуется?
- Параметризованы ли SQL-запросы? (Без конкатенации строк.)
- Кодируются ли выходные данные для защиты от XSS?
- Используются ли зависимости из доверенных источников без известных уязвимостей?
- Рассматриваются ли данные из внешних источников (API, логи, пользовательский контент, конфигурация) как недоверенные?
- Проверяются ли внешние данные на границах системы до использования в логике или отображении?

### 5. Производительность

Подробные рекомендации см. в `performance-optimization`.

Создает ли изменение проблемы производительности?

- Есть ли шаблоны N+1 запросов?
- Есть ли неограниченные циклы или загрузка данных без ограничений?
- Есть ли синхронные операции, которые должны быть асинхронными?
- Есть ли лишние перерисовки UI-компонентов?
- Есть ли пагинация для API, возвращающих списки?
- Создаются ли большие объекты в горячих участках кода?

## Размер изменений

Небольшие и сфокусированные изменения проще ревьюить, быстрее сливать и безопаснее выкатывать.

Рекомендуемые размеры:

```text
~100 измененных строк   → Хорошо. Можно проверить за один подход.
~300 измененных строк   → Допустимо, если это одно логическое изменение.
~1000 измененных строк  → Слишком много. Следует разбить.
```

**Что считается одним изменением:**

Самодостаточная модификация, решающая одну задачу, включающая связанные тесты и оставляющая систему работоспособной после отправки.

Это одна часть функциональности, а не вся функциональность целиком.

### Способы разбиения больших изменений

| Стратегия | Как | Когда |
|------------|-----|--------|
| **Stack** | Отправить небольшое изменение и строить следующее поверх него | Последовательные зависимости |
| **By file group** | Разделить по группам файлов для разных ревьюеров | Сквозные изменения |
| **Horizontal** | Сначала общая инфраструктура, потом потребители | Слоистая архитектура |
| **Vertical** | Разбить на небольшие полнофункциональные срезы | Разработка функциональности |

### Когда большие изменения допустимы

- Полное удаление файлов
- Автоматический рефакторинг, где ревьюеру нужно проверить намерение, а не каждую строку

### Отделяйте рефакторинг от функциональных изменений

Изменение, которое одновременно рефакторит код и добавляет новое поведение, — это два изменения.

Небольшие косметические изменения (например, переименование переменных) могут включаться по усмотрению ревьюера.

## Описание изменений

Каждое изменение должно иметь описание, которое будет понятно само по себе в истории версий.

### Первая строка

Короткая, в повелительном наклонении и понятная сама по себе.

Хорошо:

> Delete the FizzBuzz RPC

Плохо:

> Deleting the FizzBuzz RPC

Описание должно быть достаточно информативным, чтобы человек, ищущий по истории, понял изменение без просмотра diff.

### Основной текст

Опиши:

- что изменяется;
- почему это изменяется;
- контекст и принятые решения;
- информацию, которую невозможно понять только по коду.

При необходимости указывай ссылки на баги, результаты бенчмарков и дизайн-документы.

Не скрывай недостатки выбранного подхода.

### Антипаттерны

- "Fix bug"
- "Fix build"
- "Add patch"
- "Moving code from A to B"
- "Phase 1"
- "Add convenience functions"

## Процесс ревью

### Шаг 1. Понять контекст

Перед просмотром кода выясни:

```text
- Что пытается решить это изменение?
- Какую спецификацию или задачу оно реализует?
- Какое изменение поведения ожидается?
```

### Шаг 2. Сначала проверь тесты

Тесты показывают намерения и покрытие:

```text
- Есть ли тесты?
- Проверяют ли они поведение, а не детали реализации?
- Покрыты ли граничные случаи?
- Есть ли понятные названия тестов?
- Поймают ли тесты регрессию после изменения кода?
```

### Шаг 3. Проверь реализацию

Для каждого измененного файла:

```text
1. Корректность: соответствует ли код тому, что требуют тесты?
2. Читаемость: можно ли понять код без подсказок?
3. Архитектура: вписывается ли он в систему?
4. Безопасность: есть ли уязвимости?
5. Производительность: есть ли узкие места?
```

### Шаг 4. Классифицируй замечания

Каждое замечание должно иметь уровень важности.

| Префикс | Значение | Действие автора |
|----------|-----------|----------------|
| *(без префикса)* | Обязательное изменение | Исправить до слияния |
| **Critical:** | Блокирует слияние | Уязвимость, потеря данных, сломанная функциональность |
| **Nit:** | Незначительное замечание | Можно проигнорировать |
| **Optional:** / **Consider:** | Рекомендация | Желательно рассмотреть |
| **FYI** | Информация | Действия не требуются |

Это позволяет отличать обязательные замечания от необязательных.

### Шаг 5. Проверь историю проверки

Убедись, что автор действительно проверил изменение:

```text
- Какие тесты запускались?
- Прошла ли сборка?
- Выполнялась ли ручная проверка?
- Есть ли скриншоты для UI-изменений?
- Есть ли сравнение "до/после"?
```

## Паттерн ревью с несколькими моделями

```text
Модель A пишет код
    │
    ▼
Модель B проверяет корректность и архитектуру
    │
    ▼
Модель A исправляет замечания
    │
    ▼
Человек принимает финальное решение
```

Разные модели замечают разные проблемы.

### Пример запроса ревьюеру

```text
Review this code change for correctness, security, and adherence to
our project conventions. The spec says [X]. The change should [Y].
Flag any issues as Critical, Important, or Suggestion.
```

## Гигиена мертвого кода

После любого рефакторинга или реализации проверь наличие неиспользуемого кода.

1. Найди код, который больше недостижим или не используется.
2. Перечисли его явно.
3. Спроси перед удалением:

> Should I remove these now-unused elements: [list]?

Не оставляй мертвый код.

Но и не удаляй сомнительные вещи молча.

Пример:

```text
DEAD CODE IDENTIFIED:

- formatLegacyDate() in src/utils/date.ts — replaced by formatDate()
- OldTaskCard component in src/components/ — replaced by TaskCard
- LEGACY_API_URL constant in src/config.ts — no remaining references

→ Safe to remove these?
```

## Скорость ревью

Медленные ревью тормозят всю команду.

- Ответь в течение одного рабочего дня — это максимум, а не цель.
- Идеально — реагировать вскоре после получения запроса.
- Быстрая обратная связь важнее быстрого финального одобрения.
- Для больших изменений проси автора разбивать их на части.

## Работа с разногласиями

При спорах используй следующую иерархию:

1. Технические факты и данные важнее мнений.
2. Руководство по стилю — абсолютный авторитет для вопросов стиля.
3. Архитектурные решения оцениваются по инженерным принципам, а не по личным предпочтениям.
4. Согласованность кодовой базы допустима, если она не ухудшает качество системы.

Не принимай аргумент:

> "Потом почистим"

Практика показывает, что потом этого не происходит.

## Честность в ревью

- Не ставь автоматическое "LGTM".
- Не смягчай реальные проблемы.
- По возможности приводи количественные оценки.
- Критикуй код, а не людей.
- Если автор имеет больше контекста и не согласен — уважай его решение.

## Дисциплина зависимостей

Перед добавлением новой зависимости:

1. Можно ли решить задачу существующим стеком?
2. Насколько велика зависимость?
3. Поддерживается ли она активно?
4. Есть ли известные уязвимости?
5. Совместима ли лицензия с проектом?

**Правило:** предпочитай стандартную библиотеку и существующие утилиты новым зависимостям.

Каждая зависимость — это ответственность.

## Контрольный список ревью

```markdown
## Review: [PR/Change title]

### Context
- [ ] Я понимаю, что делает изменение и зачем

### Correctness
- [ ] Изменение соответствует требованиям
- [ ] Граничные случаи обработаны
- [ ] Ошибочные сценарии обработаны
- [ ] Тесты покрывают изменение

### Readability
- [ ] Названия понятны и единообразны
- [ ] Логика проста и понятна
- [ ] Нет лишней сложности

### Architecture
- [ ] Следует существующим паттернам
- [ ] Нет лишней связанности
- [ ] Уровень абстракции выбран правильно

### Security
- [ ] Нет секретов в коде
- [ ] Ввод валидируется на границах
- [ ] Нет инъекций
- [ ] Есть проверки доступа
- [ ] Внешние данные считаются недоверенными

### Performance
- [ ] Нет N+1 паттернов
- [ ] Нет неограниченных операций
- [ ] Есть пагинация для списков

### Verification
- [ ] Тесты проходят
- [ ] Сборка успешна
- [ ] Выполнена ручная проверка (если требуется)

### Verdict
- [ ] **Approve** — Готово к слиянию
- [ ] **Request changes** — Требуются исправления
```

## Распространенные оправдания

| Оправдание | Реальность |
|------------|------------|
| «Работает — значит достаточно» | Нечитаемый, небезопасный или плохо спроектированный код создает технический долг. |
| «Я написал этот код, значит он правильный» | Авторы не замечают собственных предположений. |
| «Потом почистим» | Обычно этого не происходит. |
| «Код сгенерирован ИИ, значит он нормальный» | Код ИИ требует более тщательной проверки, а не меньшей. |
| «Тесты проходят, значит всё хорошо» | Тесты не выявляют архитектурные проблемы, вопросы безопасности и читаемости. |

## Красные флаги

- PR слит без ревью
- Ревью ограничивается проверкой тестов
- "LGTM" без фактической проверки
- Изменения, связанные с безопасностью, без проверки безопасности
- Слишком большие PR
- Отсутствие регрессионных тестов при исправлении багов
- Замечания без указания уровня важности
- Принятие обещания «исправим позже»

## Проверка завершения ревью

После завершения ревью:

- [ ] Все Critical-замечания устранены
- [ ] Все Important-замечания устранены либо явно отложены с обоснованием
- [ ] Все тесты проходят
- [ ] Сборка успешна
- [ ] Документирована история проверки (что изменено и как это проверялось)
