# Разработка на основе спецификаций (Spec-Driven Development)

## Обзор

Пиши структурированную спецификацию перед написанием любого кода. Спецификация — это общий источник истины между тобой и разработчиком-человеком. Она определяет, что мы создаем, зачем и как мы поймем, что задача выполнена. Писать код без спецификации — это гадание.

## Когда использовать

- Запуск нового проекта или фичи
- Требования двусмысленны или неполны
- Изменение затрагивает несколько файлов или модулей
- Ты собираешься принять архитектурное решение
- На реализацию задачи уйдет более 30 минут

**Когда НЕ использовать:** Правки в одну строку, исправление опечаток или изменения, в которых требования однозначны и самодостаточны.

## Рабочий процесс с контрольными точками (Gated Workflow)

Разработка на основе спецификаций состоит из четырех этапов. Не переходи к следующему этапу, пока не будет утвержден текущий.

```
СПЕЦИФИКАЦИЯ ──→ ПЛАН ──→ ЗАДАЧИ ──→ РЕАЛИЗАЦИЯ
     │             │         │            │
     ▼             ▼         ▼            ▼
 Проверка      Проверка  Проверка     Проверка
 человеком     человеком человеком    человеком
```

### Этап 1: Спецификация (Specify)

Начни с общего видения. Задавай человеку уточняющие вопросы, пока требования не станут конкретными.

**Сразу выявляй предположения.** Перед написанием спецификации перечисли то, что ты предполагаешь:

```
МОИ ПРЕДПОЛОЖЕНИЯ:
1. Это веб-приложение (не нативное мобильное)
2. Аутентификация использует cookie на основе сессий (не JWT)
3. База данных — PostgreSQL (на основе существующей схемы Prisma)
4. Мы ориентируемся только на современные браузеры (без IE11)
→ Поправь меня сейчас или я продолжу работу с этими предположениями.
```

Не заполняй неясные требования молча. Главная цель спецификации — выявить недопонимание *до* написания кода. Предположения — самая опасная форма недопонимания.

**Напиши спецификацию, охватывающую следующие шесть ключевых областей:**

1. **Цель (Objective)** — Что мы создаем и зачем? Кто пользователь? Как выглядит успех?

2. **Команды (Commands)** — Полные исполняемые команды с флагами, а не просто названия инструментов.
   ```
   Сборка: npm run build
   Тесты: npm test -- --coverage
   Линтер: npm run lint --fix
   Разработка: npm run dev
   ```

3. **Структура проекта (Project Structure)** — Где живет исходный код, куда класть тесты и документацию.
   ```
   src/           → Исходный код приложения
   src/components → Компоненты React
   src/lib        → Общие утилиты
   tests/         → Юнит- и интеграционные тесты
   e2e/           → End-to-end тесты
   docs/          → Документация
   ```

4. **Стиль кода (Code Style)** — Один реальный фрагмент кода, показывающий твой стиль, лучше трех абзацев с его описанием. Включи соглашения об именовании, правила форматирования и примеры качественного вывода.

5. **Стратегия тестирования (Testing Strategy)** — Какая библиотека используется, где лежат тесты, требования к покрытию, какие уровни тестирования для каких задач.

6. **Границы (Boundaries)** — Трехуровневая система:
   - **Всегда делай:** Запускай тесты перед коммитами, следуй соглашениям об именовании, валидируй входные данные.
   - **Сначала спроси:** Изменения в схеме базы данных, добавление зависимостей, изменение конфигурации CI.
   - **Никогда не делай:** Коммитить секреты, редактировать сторонние библиотеки (vendor directories), удалять упавшие тесты без одобрения.

**Шаблон спецификации:**

```markdown
# Спецификация: [Название проекта/фичи]

## Цель (Objective)
[Что мы создаем и зачем. Пользовательские сценарии или критерии приемки.]

## Технологический стек (Tech Stack)
[Фреймворк, язык, ключевые зависимости с версиями]

## Команды (Commands)
[Сборка, тесты, линтер, запуск — полные команды]

## Структура проекта (Project Structure)
[Структура директорий с описанием]

## Код-стайл (Code Style)
[Пример кода + ключевые соглашения]

## Стратегия тестирования (Testing Strategy)
[Фреймворк, расположение тестов, требования к покрытию, уровни тестов]

## Границы (Boundaries)
- Всегда: [...]
- Сначала спроси: [...]
- Никогда: [...]

## Критерии успеха (Success Criteria)
[Как мы поймем, что задача выполнена — конкретные, проверяемые условия]

## Открытые вопросы (Open Questions)
[Все, что не решено и требует участия человека]
```

**Формулируй инструкции как критерии успеха.** Получая неточные требования, переводи их в конкретные условия:

```
ТРЕБОВАНИЕ: "Сделай дашборд быстрее"

ПЕРЕФОРМУЛИРОВАННЫЕ КРИТЕРИИ УСПЕХА:
- LCP дашборда < 2.5 с на 4G-соединении
- Начальная загрузка данных завершается менее чем за 500 мс
- Отсутствие сдвигов макета при загрузке (CLS < 0.1)
→ Верны ли эти целевые показатели?
```

Это позволит тебе итерировать, пробовать решения и двигаться к понятной цели вместо того, чтобы гадать, что означает "быстрее".

### Этап 2: План (Plan)

После утверждения спецификации составь технический план реализации:

1. Выяви основные компоненты и их зависимости.
2. Определи порядок реализации (что нужно построить в первую очередь).
3. Опиши риски и стратегии их минимизации.
4. Выдели задачи, которые можно делать параллельно, и те, которые должны выполняться последовательно.
5. Определи контрольные точки для проверки между этапами.

План должен быть удобен для ревью: человек должен прочитать его и сказать: «Да, это правильный подход» или «Нет, измени X».

### Этап 3: Задачи (Tasks)

Разбей план на отдельные, готовые к реализации задачи:

- Каждая задача должна быть выполнима за одну сфокусированную сессию.
- Каждая задача имеет четкие критерии приемки.
- Каждая задача включает шаг проверки (тест, сборка, ручная проверка).
- Задачи упорядочены по зависимостям, а не по кажущейся важности.
- Ни одна задача не должна требовать изменения более чем ~5 файлов.

**Шаблон задачи:**
```markdown
- [ ] Задача: [Описание]
  - Приемка: [Что должно быть выполнено]
  - Проверка: [Как подтвердить — команда теста, сборка, ручная проверка]
  - Файлы: [Какие файлы будут изменены]
```

### Этап 4: Реализация (Implement)

Выполняй задачи по одной, следуя `skills/incremental-implementation/SKILL.md` (`incremental-implementation`) и `skills/test-driven-development/SKILL.md` (`test-driven-development`). Используй `skills/context-engineering/SKILL.md` (`context-engineering`), чтобы загружать нужные разделы спецификации и исходные файлы на каждом шаге, а не перегружать контекст всей спецификацией сразу.

## Поддержание спецификации в актуальном состоянии

Спецификация — это живой документ, а не одноразовый артефакт:

- **Обновляй при изменении решений** — если ты обнаружишь, что модель данных нужно изменить, сначала обнови спецификацию, а затем приступай к реализации.
- **Обновляй при изменении рамок (scope)** — добавленные или вырезанные фичи должны отражаться в спецификации.
- **Коммить спецификацию** — она должна храниться в системе контроля версий рядом с кодом.
- **Ссылайся на спецификацию в PR** — давай ссылку на раздел спецификации, который реализует данный PR.

## Распространенные оправдания

| Оправдание | Реальность |
|---|---|
| «Это просто, мне не нужна спецификация» | Простые задачи не требуют *длинных* спецификаций, но им все равно нужны критерии приемки. Двух строк достаточно. |
| «Я напишу спецификацию после того, как напишу код» | Это документирование, а не проектирование. Смысл спецификации в том, чтобы внести ясность *до* написания кода. |
| «Спецификация замедлит нас» | 15 минут на спецификацию сберегут часы переделок. 15 минут планирования лучше 15 часов отладки. |
| «Требования все равно изменятся» | Поэтому спецификация — это живой документ. Устаревшая спецификация все равно лучше, чем ее отсутствие. |
| «Пользователь знает, чего хочет» | Даже у понятных запросов есть скрытые предположения. Спецификация выявляет эти предположения. |

## Красные флаги

- Начало написания кода без каких-либо зафиксированных требований.
- Вопрос «Может, мне просто начать писать код?» до уточнения того, что означает «задача выполнена».
- Реализация фич, не упомянутых в спецификации или списке задач.
- Принятие архитектурных решений без их документирования.
- Пропуск спецификации, потому что «и так очевидно, что делать».

## Проверка

Перед тем как перейти к реализации, подтверди:

- [ ] Спецификация охватывает все шесть ключевых областей.
- [ ] Человек изучил и утвердил спецификацию.
- [ ] Критерии успеха конкретны и проверяемы.
- [ ] Границы (Всегда/Сначала спроси/Никогда) определены.
- [ ] Спецификация сохранена в файл в репозитории.
